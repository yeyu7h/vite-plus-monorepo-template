# 多业务应用开发规范

本文约定在同一个 Vite+ monorepo 中创建、开发、维护和发布多个业务应用的基本规则，供开发者和 AI 编码代理共同使用。各应用可以补充业务专属约定；修改这些约定时应保持与仓库规范及对应目录的 `AGENTS.md` 一致。

文中的命令均从仓库根目录执行。`order`、`member` 及其应用名称仅作为示例；创建应用之后才能运行对应命令。

## 1. 仓库与应用边界

```text
apps/
  order-web/          # 订单业务前台
  order-admin/        # 订单业务管理端
  order-api/          # 订单业务 API
  member-web/         # 会员业务前台
  member-api/         # 会员业务 API
templates/            # 新应用的模板
packages/             # 公共能力及必要的共享契约
internal/             # 仓库内部工程配置和测试支持
examples/             # 可参考的完整示例
```

- 一个可独立构建或运行的前端、管理端或 API 对应一个应用；按需创建，不强制每个业务都拥有全部三种应用。
- 应用名使用小写字母、数字和连字符，以字母开头，推荐 `<业务>-<类型>`，例如 `order-api`。workspace 包名为 `@app/<应用名>`。
- 业务专属页面、接口、规则、配置和数据模型留在对应应用。公共组件、工具和稳定的跨应用能力放在职责明确的 `packages/` 中。
- 应用之间不直接导入对方的内部源码或访问对方的数据库。跨业务协作通过明确的服务接口、事件或共享契约进行，并约定兼容性和数据归属。
- 共享包从自己的公开入口导出能力，不依赖某个应用的私有源码、环境或全局实例；有应用差异时，通过参数、接口或依赖注入表达。
- 避免循环依赖。`internal/` 用于仓库内部的工程配置与测试支持，具体依赖关系遵循各包的职责。
- 目前工作区、测试发现和脚手架使用 `apps/*` 扁平结构。若将来需要 `apps/order/api` 这样的嵌套结构，先同步调整工作区、测试发现、脚手架及相关构建配置。
- 仓库目录和分支不是源码访问权限边界。有独立源码访问或交付要求的业务，应评估单独仓库。

## 2. 创建业务应用

从现有模板创建所需应用，例如：

```bash
vp run create:app -- web order-web
vp run create:app -- admin order-admin
vp run create:app -- api order-api
vp install
```

创建后：

1. 为应用补充 README，说明业务职责、负责人、启动方式、端口、依赖服务、环境变量、测试和部署方式。
2. 为 API 配置独立的数据库、Redis、密钥及其他必要服务；根据应用实际需要配置对象存储和第三方平台。
3. 为同时运行的应用分配不冲突的端口，并配置前端代理、API 地址及类型生成地址，确认它们指向预期 API。
4. 检查该应用的 `.gitignore`、环境文件和模板残留的默认配置，确认不会提交真实凭据。
5. 记录创建时使用的模板类型和 Git 提交，方便后续评估模板改动；当前脚手架不会自动记录或同步模板版本。

启动示例：

```bash
vp run @app/order-web#dev
vp run @app/order-api#dev
```

脚手架创建的是模板的独立副本，不会自动把后续模板修改同步到已有应用。现有模板覆盖 Web、管理端和 API；原生移动端及小程序前端需要另行接入相应工具和模板。

## 3. 分支、提交与代码评审

- `main` 是共同集成分支，保持可检查、可构建。每项功能、修复或维护任务从最新的 `main` 创建短期分支，完成后通过 Pull Request 合并。
- 分支名包含业务和目的，例如 `feature/order-refund`、`fix/member-login`。AI 代理创建分支时同时遵循其运行环境的分支命名要求，例如 `codex/order-refund`。
- 不为每个业务长期维护独立开发分支。需要维护特定已发布版本时，可按需建立发布分支，并将适用的修复合回 `main`。
- 尚未准备开放的功能应拆分为可独立验证的改动；需要时使用功能开关，确保合并后的默认行为可控。
- 提交信息使用 `<类型>(<范围>): <说明>`，例如 `feat(order-api): add refund endpoint`、`fix(request): handle expired token`。范围优先使用应用或共享包名称。
- Pull Request 至少说明变更目的、受影响的应用和共享包、验证结果，以及是否涉及迁移、环境变量、发布或回滚。多人协作时邀请相关负责人审查。
- 合并前检查通过；分支保护及强制评审需要在实际使用的代码托管平台上配置。

## 4. 工具链与依赖

- 使用仓库声明的 Node.js、pnpm 和 Vite+ 版本约束；CI 使用 Node 24。拉取远端更改后执行 `vp install`。
- `vp <命令>` 是 Vite+ 内置命令；运行项目定义的脚本或任务使用 `vp run <名称>`。执行前检查目标项目的 `package.json` 和 `vite.config.ts`。
- 每个应用或包显式声明直接依赖；仓库内部包使用 workspace 依赖。共享第三方依赖优先遵循 `pnpm-workspace.yaml` 中现有 catalog 与 overrides 的约定。
- 依赖增删或升级时提交对应的 `pnpm-lock.yaml` 变化，并检查受影响的消费方。避免顺手进行无关的大范围升级。
- 共享包保持清晰、可测试的公开接口；变更接口时说明兼容性和受影响应用。不要为一次性的业务逻辑机械地创建公共包。

## 5. 代码与接口

- 格式、Lint 和类型检查以仓库 Vite+ 配置为准。优先使用明确类型和现有项目约定，避免无必要的 `any`、重复实现和跨层耦合。
- 前端遵循已有路由、组件和请求封装；界面状态应覆盖加载、空结果和错误，交互兼顾键盘和基础可访问性。
- API 沿用应用现有的路由、Schema、处理器和服务划分；优先从 Zod Schema 推导类型。响应、状态码、日志和错误处理遵循目标 API 的 `AGENTS.md`。
- 公共、客户端和管理端接口分别使用其对应的认证与授权策略。默认 API 的客户端认证在配置业务适配器前拒绝访问；不要为了方便调试跳过正式的认证或权限判断。
- 后端校验来自客户端或外部系统的数据；日志保留排障所需上下文，避免记录密码、令牌和其他敏感数据。
- 涉及后台任务时明确重试、幂等、失败处理和调度归属；多实例场景需验证不会意外重复处理业务操作。
- 接口或契约变更应考虑已有调用方的兼容性，并同步维护需要更新的 OpenAPI 类型及相关文档。

## 6. 配置、密钥与环境隔离

- 开发、测试、生产使用各自的配置和服务资源；每个业务使用独立的密钥与访问凭据，按需授予权限。
- `.env.example` 只包含可公开的示例或占位值；真实密钥通过本地受忽略文件或部署环境的密钥管理提供。前端 `VITE_*` 配置会进入客户端产物，不得存放密钥。
- 先核对应用的 Git 忽略规则，再创建本地配置，并用 `git status` 等方式检查待提交内容。被忽略不等于加密，已被 Git 跟踪的文件也不会因为新增忽略规则而自动停止跟踪。
- 当前 API 模板有自己的 `.env` 忽略规则，Web 和管理端的规则并不相同；不要假设所有应用的 `.env` 文件都会被忽略。模板及其可能被脚手架复制的文件中均不得包含真实凭据。
- 使用模板时检查端口、数据库 URL、Redis URL、前端代理、OpenAPI 地址、对象存储和第三方回调地址，避免多个业务误连同一服务或环境。
- 多个业务并行使用 Compose 时，分别检查项目名、端口、数据卷、镜像名及环境文件，避免资源冲突。

## 7. 数据库、Redis 与外部资源

- 默认每个业务 API 使用独立数据库、账号和迁移历史。当前 API 模板使用相同的表结构和迁移表名称，不能直接把多个应用指向同一个数据库；若确需共享，必须先设计并验证隔离与迁移方案。
- 不修改已在目标环境执行的迁移 SQL 和快照；通过新的迁移演进。已有业务继续使用自己的迁移链，不用通用模板的初始迁移替换历史。参见 [数据库迁移边界](../templates/template-api/migrations/README.md)。
- `push` 仅用于确认可变更的开发数据库；测试和生产通过审查过的迁移文件演进。执行迁移、seed 或其他写操作前确认目标应用、环境和数据库，并根据变更准备备份及恢复方案。
- 数据库改动应考虑应用新旧版本并存、数据回填和回滚。代码回滚不等于数据库自动回滚；不兼容或破坏性变更需要单独规划。
- Redis 默认优先按业务和环境使用独立实例。若共享实例，必须对缓存键、队列及其调度、锁、限流和 Pub/Sub 通道等完整设计应用命名空间，并验证缓存管理和清理范围。
- 仅使用不同的 Redis 逻辑数据库不能隔离 Pub/Sub 通道。当前模板含固定缓存键、BullMQ 前缀和 Casbin 通道，不能假定复制出的应用可直接安全共用 Redis。调整已有队列命名时应处理存量任务和切换过程。
- 对象存储、消息服务和第三方平台按业务和环境划分凭据及资源范围，明确文件归属、数据保留和清理方式。

## 8. 测试与持续集成

提交前完成与改动相适应的验证。全仓基线为：

```bash
vp run ready
```

该命令依次运行 `vp check`、脚手架测试、根级 `vp test` 和工作区构建。目标目录的 `AGENTS.md` 可能要求额外检查；例如 API 模板还要求 `vp run -r test`。

- 默认测试不依赖 PostgreSQL 或 Redis。新增测试重点覆盖业务行为、边界和回归，不为每处简单改动机械地增加重复测试。
- 涉及数据库、Redis、队列、存储或外部服务时，使用各应用的集成测试与专用测试资源；测试环境不得指向生产资源。
- API 模板的数据库集成测试需要先准备专用数据库和 Redis、完成必要迁移及 seed，并显式配置 `TEST_DATABASE_URL` 和 `TEST_REDIS_URL`。创建 `order-api` 后，可运行 `vp run @app/order-api#test:integration`；对象存储测试按该应用的配置单独执行。
- 修改共享包、模板、根配置或锁文件时，检查所有可能受影响的应用；需要真实服务的行为不能仅凭默认单元测试判定通过。
- 当前 GitHub 和 Gitea 工作流执行全仓 `ready`，不自动运行外部服务集成测试或部署。应用数量增长后可建设基于依赖关系的增量检查，但公共依赖及根配置变化仍需扩大验证范围。

## 9. 模板改进与共享包回流

业务开发中发现问题时，先判断来源、适用范围及已有应用的影响：

| 改动                                       | 处理方式                                   |
| ------------------------------------------ | ------------------------------------------ |
| 仅适用于当前业务的规则或功能               | 留在对应应用中。                           |
| 模板自身存在的缺陷或普遍适用的默认配置改进 | 修复模板，并检查和处理受影响的已有应用。   |
| 已有共享包中的通用缺陷或能力               | 修改共享包，验证所有受影响的消费方。       |
| 多个应用需要、边界清晰且适合共同维护的逻辑 | 考虑抽取共享包，并让模板及适用的应用接入。 |

具体流程：

1. 定位问题是在业务代码、模板副本还是现有共享包中；安全或影响生产的问题先处理受影响应用。
2. 判断通用性及兼容性。模板仍有同类问题时同步修复模板；需要复用且边界合适时提取或完善共享包。
3. 检查其他已创建应用，按其实际差异选择性移植，不直接用整个模板覆盖业务代码。涉及数据库或队列状态时制定单独的迁移方案。
4. 对关键行为补充有意义的回归验证，并检查脚手架生成的新应用是否仍符合预期。
5. 在 PR 或变更记录中说明模板、共享包和应用的影响范围，以及哪些已有应用需要跟进。

模板修改只影响之后生成的副本。共享包使用 workspace 依赖时，消费方在后续构建中会使用该工作区的包；已经部署的应用不会自动更新，必须完成自身验证和发布。当前没有模板自动同步或版本追踪机制。

## 10. 构建与发布

- 应用分别构建、配置和发布。记录应用名、环境、源码 Git 提交、构建产物或镜像标识、部署时间和执行结果，确保可以定位运行版本。
- 例如，创建 `order-api` 后，可以用 `vp run -t @app/order-api#build` 构建该应用及其依赖。发布方式以应用实际的构建产物和部署配置为准。
- 发布前确认目标环境、配置与密钥、依赖服务、健康检查、迁移顺序、验证方式和回滚或恢复方案。跨应用接口变更先考虑兼容，再分别安排发布。
- 共享包的修改需要评估所有消费方；是否发布某个应用由该应用的变更和发布计划决定。不要假定合并 `main` 后所有应用已经部署。
- 当前仓库提供 API Docker 构建示例和全仓 CI，尚未提供按应用自动部署、部署审批或发布记录系统；上述发布流程需要结合实际环境实现。

## 11. AI 协作与规范维护

- AI 代理先读取根目录和目标目录适用的 `AGENTS.md`，遵循本文及仓库适用的技能。CRUD、数据库 Schema、Drizzle、BullMQ、Effect、API tier 和 Nuxt UI 等任务使用对应的仓库技能。
- AI 与人工开发使用相同的业务边界、测试和安全要求；不得把业务专属实现直接放进通用模板或共享包。
- 发现已有规范与实际实现不一致时，先确认影响和预期，再同步更新相关规范或实现，不默认为模板副本已经更新。
- 本文维护全仓通用约定；应用 README 和就近 `AGENTS.md` 维护应用专属细节。共享规则变化时检查模板中的指导文件，避免新建应用继续复制过期说明。
- 当前优先建设项包括：统一各类应用的环境文件保护、多应用资源隔离、按依赖范围验证、模板变更追踪，以及按应用发布。完成后同步更新本文和相应自动化的状态。

## 12. 合并前检查清单

- [ ] 改动放在正确的业务应用、模板或共享包中，并已评估是否需要回流和同步已有应用。
- [ ] 已检查受影响的应用、共享依赖和接口兼容性；需要时记录后续移植事项。
- [ ] 配置、日志、示例和待提交文件不包含真实密钥或业务敏感数据。
- [ ] 已执行适用的 `vp run ready`、目标目录额外检查和必要的专用服务集成测试；未运行的检查及原因已说明。
- [ ] 数据库、队列、环境变量或部署有变化时，已说明迁移、验证及回滚或恢复方案。
- [ ] PR 包含变更目的、影响范围和验证结果，相关文档已更新。
